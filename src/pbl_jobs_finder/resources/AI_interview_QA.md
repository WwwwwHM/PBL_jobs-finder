# AI大模型应用开发面试题库

## 1. 什么是AI Agent？ 它和直接调用大模型API有什么区别？

AI Agent是一个能感知环境、拆解任务、调用工具的自主系统，它用LLM作为大脑，各种工具作为四肢五官来完成用户交代的各种任务；而直接调用大模型API本质上是在跟LLM对话，只会一问一答，用户输入prompt，LLM吐出一段回答，其他的操作全靠用户自己完成。

本质上的差异是
1、AI Agent会用ReAct循环作为思考范式，通过“推理-调用-观察”作为一个循环周期不断循环思考直至解决问题；API调用LLM则是单链路的对话问答，不存在循环链路

2、AI Agent有记忆功能，能支持上下文对话，不需要每次输入历史对话；API调用LLM不包含记忆功能，每次对话都是新的记忆，需要把历史内容全部输入到提示词里

3、AI Agent能调用外部工具，能够通过调用工具来与外界互动、了解外界信息；API调用LLM则无法调用工具，只能输入输出文本信息，无法与外界互动

### 1.1 追问：ReAct 这个循环具体是怎么实现的？模型怎么知道什么时候该停下来？

实现上就是一个while循环，每一轮会把当前任务描述、历史对话记录、上一步工具调用返回结果拼接成prompt喂给模型。模型按照格式输出thought、Action、Action input三个字段，框架解析出来之后调用对应工具，工具返回的结果作为observation拼入prompt进入下一个循环。

停止条件一般有两种：一种是模型拿到observation后判断问题已经解决，输出final answer标记，表示任务完成了；另一种是循环次数超过上限，模型强行停止思考，LangChain默认上限为15轮。


### 1.2 追问：Agent现在最大的问题是什么？ 实际落地效果怎么样？

目前Agent最大的问题是不可控，模型推理能力不稳定，复杂问题拆解经常出错，工具调用的参数也可能瞎填，中间有一步跑偏后面就越走越偏。

实际落地不会纯靠Agent，而是人为设定好任务节点，拆解出各个小问题让Agent执行，属于是在自主性和可控性之间进行工程化平衡。目前claude code、codex等编程类Agent的落地成果案例较多，因为编程任务的逻辑性强，代码有明确的测试验收流程。

### 1.3 追问：Function Calling 和 Tool Calling 有什么区别？

严格来说没什么区别，最早openai把工具调用命名为Function Calling，后来2023年改名为Tool Calling，应该是想表达模型调用的不只是函数。实际底层都是模型输出一段结构化的JSON，包含需要调用什么工具、传什么参数，由应用层解析去执行然后再返回结果回来。

## 2. AI Agent的核心组件有哪些？感知、决策、执行、记忆各自的作用是什么？

一个完整的Agent通常由四个核心组件组成：感知、决策、执行、记忆。

感知组件的作用是让Agent能够接受和理解外部的信息，输入大多数是自然语言指令，但也可能有图片、文件内容、API返回的结构化数据等，这就要通过各种工具调用把多模态的输入解析成统一的结构化JSON给LLM读取。

决策组件就是LLM，是agent的大脑，利用LLM的推理能力理解当前任务，分析已有信息，做出下一步要做什么的自主决策。比如用户说“帮我分析这份消息报表。”，决策组件就会判断出：先读文件，再提取关键信息，分析信息，最后生成分析报告。整个任务的拆解和编排都靠它。

执行组件的作用是把决策转成实际行动。最典型的就是工具调用，解析LLM的输出并调用相关工具执行任务并返回工具调用结果供LLM进行下一步决策。比如跑代码、查数据库、调外部API、读写文件都是执行组件的活。

记忆组件的作用就是让agent能记住历史信息。短期记忆就是当前对话的上下文，记录本次任务已经做了什么、拿到了什么结果。长期记忆则是把重要信息持久化保存下了，下次会话还能用。没有记忆的Agent每一步都像失忆一样，效率很低。

### 2.1 追问：短期记忆塞满了怎么办？上下文窗口不够用的时候有什么解决方案？

常用的策略有三种。第一种是滑动窗口，只保留最近的N条信息，其余的全丢掉，这个方法简单粗暴但是会丢信息；第二种是摘要压缩，每隔一段让模型把会话压缩成一段摘要，用摘要替换掉原文。第三章是检索式记忆，把所有历史会话全部存入向量数据库中，每轮对话开始时根据当前问题检索最相关的几条历史塞进上下文。实际项目中一般摘要和检索配合使用，效果最好。

### 2.2 追问：如果决策模块选错了工具，或者工具调用失败了，Agent怎么处理？

好的Agent框架自带错误恢复机制。工具调用失败后执行模块会返回错误信息给决策模块，决策模块分析错误信息重新规划，可能换个工具或者更换参数重试。比如查数据库时SQL语法报错，LLM看到错误信息后修正错误再试一次。通常会有一个最大重试次数，一般设置3-5次，超过次数就更换别的方案。选错工具也类似。不过模型的纠错能力有限，复杂场景下还是需要依靠人工设置兜底逻辑。

### 2.3 追问：多个Agent协作的时候，它们的记忆是怎么共享的？

多个Agent记忆共享一般有两种模式。一种是共享黑板，所有Agent的记忆放到一个公共存储中共享读写，类似多人协作文档，比如CrewAI。另一种是消息传递，Agent之间通过结构化消息通信，每个Agent有自己独立的记忆空间，只有通过消息才能获取别人的信息，比如AutoGen，Agent之间的对话记录就是消息传递的载体。共享黑板简单但容易消息爆炸，消息传递隔离性好但是通信开销大，得根据实际场景选择。

## 3. 什么是AI Agent中的工具调用（Tool Calling）？ 它的基本流程是怎样的？

工具调用是Agent与外部世界交互的核心机制。就是让大模型在需要的时候，自己决定调用什么工具、传什么参数，然后根据工具返回的结果继续推理。这是Agent从“只能说”到“能做事”的关键能力。

基本流程分四步：

1）先告诉模型有什么工具可用，每个工具干什么、参数是什么格式，这些信息随Prompt一起发给模型。

2）模型在对话中判断当前情况需要用某个工具，输入结构化的JSON，里面包含工具名和参数值。但是模型自己不执行任何操作，它只说要用什么工具。

3）应用层接收并解析这段JSON，执行操作后返回结果给模型。比如调API、跑SQL、读文件。

4）模型拿到结果后要么返回答案，要么继续调用别的工具。

举个例子，用户问“帮我查一下苹果公司今日股价”。模型不会瞎编一个数字，而是生成一段调用股价查询API的请求，应用层执行这个API拿到真实数据，再把数据喂回给模型，模型用真实数据来回答。

### 3.1 追问：如果模型输出的工具调用参数格式不对，JSON解析失败了怎么办？

分两层处理，第一层是解析容错，设置宽松JSON解析器，能自动修复常见的JSON格式错误，比如少个逗号，缺个引号。LangChain里就有专门的OutputFixingParser来做这个事。

第二层是重试机制，把错误信息拼回prompt，告诉模型“你上次的JSON格式有错误，正确的格式是这样的”，让它重新生成，一般重试2-3次就能拿到正确格式。如果用原生Function Calling 而不是 Prompt 注入方式，格式出错的概率就低很多，因为模型会在训练的时候就学习过这个格式。

### 3.2 追问：模型怎么处理一个工具的输出特别长的情况？比如搜索返回了几万字的结果？

首先直接把几万字上下文塞入prompt肯定不行，既浪费token又容易干扰模型判断，常见的作法是做截断或者摘要。最简单的就是截取前N个字符，比如只取前2000字。更好的方式是先用一个快速模型做摘要提取信息，再把摘要喂给主模型。

### 3.3 追问：MCP 协议和 OpenAI 的 Function Calling到底有什么本质区别？

Function Calling是解决“模型怎么调用工具”的模型侧问题，主要是指模型调用工具的一个流程；MCP是解决“工具怎么接入Agent”的工具侧问题，主要是定义了一种统一的工具调用协议标准，可以实现一次工具封装可以用于多种Agent框架比如codex、claude code。两者并不冲突，底层模型依然走的是Function Calling输出调用请求，MCP负责在上面加一层标准化的工具注册和通信协议。

### 3.4 追问：工具调用和 RAG 检索有什么关系？ 能不能把RAG理解成一种特殊的工具调用？

完全可以看作是工具调用。RAG 检索的流程本质上就是调用了检索工具，只不过早期的 RAG 检索工具被写死在了流程里，每次对话都会调用一次 RAG 检索工具。现在的 Agent 框架则把 RAG 检索作为一个普通的工具来使用，模型自己判断能解决的问题不会用到 RAG，需要使用 RAG 的时候再去调用，这样更灵活。LangChain 里的Retriever Tool就是把 RAG 封装成了一种检索工具。

## 4. 什么是 Agent 的上下文窗口？ 为什么它是 Agent 工程中最核心的约束？

上下文窗口就是大模型一次能够处理的文本长度上限，一般用token数来衡量。主流的旗舰模型一般在 200K~1M token 之间不等。对于 Agent 来说上下文窗口里塞的东西非常多：系统提示词、工具定义、对话历史、工具返回结果、中间推理过程，全部挤在这样一个有限的空间里。

它是 Agent 工程中最核心的约束的原因有3点：

1. Agent是多轮执行的。每一轮都会生成新内容：思考内容、工具调用、返回结果，不断累积。一个复杂的任务跑个 20-30 轮循环，上下人轻松膨胀到几十万 token，很快装到天花板。

2. 窗口大不等于好用。研究表明模型在超长上下文中会注意力衰减，中间部分的信息容易被忽略，这就是`Lost in the Middle`问题。塞了10万 token 进去，模型可能只对头尾各 1-2 万的token 敏感。

3. 上下文长度直接决定成本和延迟。token 越多 API 费用越高、推理越慢。一个不做上下文管理的 Agent 跑个复杂任务，一次对话花掉 5-10 美元 API 费用很常见，响应时间也从几秒拉到几十秒。

### 4.1 追问：实际项目中怎么监控 Agent 的上下文使用情况？到了上限怎么办？

一般在 Client 层做 token 计数，每轮循环算一下当前已用量。接近阈值时触发压缩：先压缩最早的几轮对话为摘要，如果还不够就截断工具返回结果。如果压缩完了还是超了，就得结束当前会话、把关键上下文持久化到文件，开一个新会话继续。Cursor 和 Claude Code 都有类似的自动 compact 逻辑。

### 4.2 追问：Lost in the Middle 问题有没有什么工程上的缓解办法？

最直接的办法是把最重要的信息放在上下文的开头和结尾。系统提示词放开头，当前轮次的关键信息放末尾，中间放不太重要的历史。还有一种做法是在关键信息旁边加显式标记，比如“[重要] 用户的核心需求是 xxx”，用文本标记来引导模型注意力。不过这些都是经验性的trick，从根本上解决还是得靠模型框架改进。

### 4.3 追问：工具定义太多占 token 怎么优化？出了动态加载还有别的办法吗？

还有几个思路。一是精简工具描述，很多工具的 description 写得太罗嗦，压缩到关键信息就够了，能省 30-50% 的 token。二是工具分组，把相关工具合并成一个“超级工具”，通过参数区分子功能，比如把“查用户”“该用户”“删用户”合成一个“用户管理”工具。三是分两阶段调用，第一阶段只给模型工具名称列表，模型选完再加载完整定义，避免一次性塞入所有schema。


## 5. AI Agent 如何处理工具调用返回超大结果的问题？有哪些实用的解决方案？

#### 解决方案分三个阶段：事前控制、事中阶段、事后摘要

1. 事前控制最高效，在调用工具之前就限死返回数据的规模。数据库查询自动加LIMIT，搜索接口限制返回条数，API 请求只拿需要的字段。关键在于工具设计阶段就把 limit、fields 这些参数暴露出来，让 Agent 能主动控制粒度。

2. 事中截断是在工具返回后、送入模型前做裁剪。简单粗暴的按 token 数砍，聪明点的做法就是结构化裁断，比如保留前几条记录当样本，附上总数和统计信息，让模型知道全貌。

3. 事后摘要是额外调用一次LLM把结果压缩成关键信息。信息保留度最高，但多一次 LLM 调用的开销。适合结果虽大但关键细节不能丢的场景，比如分析一份完整的错误日志。

#### 引用机制与按需读取

更高级的方案是引入引用机制。工具返回的大结果不塞进上下文，而是存到一个临时存储里。只给模型一个引用 ID 和摘要。模型需要查看某个特定部分的详细内容，再通过引用 ID 去取。

这跟 MCP 协议中的 Resources 概念一个思路：把大数据变成按需读取的资源，而不是一股脑推送到模型面前。OpenAI 的 Assistants API 里的 file_search 工具也是类似逻辑，搜索结果先存起来，模型通过 Annotation 引用具体片段。

#### 多级压缩策略

实际生产环境中，上面几种方案往往组合使用，形成多级压缩管线：

1. 第一级：工具层面的参数控制，limit 设成 100 条

2. 第二级：返回后做结构化截断，只保留前十条样本加统计摘要

3. 第三级：如果裁断后仍超过 token 预算，再用一次 LLM 做语义压缩

每一级的 token 阈值可以根据模型上下文窗口大小动态计算。比如模型 A 有 128K 上下文，可以给工具结果留 20K 预算；模型 B 有 200K 上下文，可以宽裕一些给到40K。

#### 流式处理与提前终止

还有一种思路是流式处理。工具不一次性返回全部结果，而是流式输出，Agent边看边判断。一旦找到需要的信息就提前终止，不用等全部数据跑完。这在搜索场景特别有用，Agent 搜代码找 bug，可能看到第三条结果就定位到问题了，后面 97 条压根不用看。

LangChain 的 Tool 抽象里有个 return_direct 选项可以配合使用，Anthropic 的 tool_use 也支持再 streaming 模式下让模型决定是否继续接受后续 chunk。

### 5.1 追问：如果 Agent 需要对超大结果做聚合分析，比如统计平均值、找最大最小值，截断和摘要都会丢信息，怎么处理？

最靠谱的做法是把聚合逻辑下推到工具层。因为让 Agent 拿到全部数据再自己算，不如再工具里直接支持聚合查询参数，比如 SQL 工具支持 GROUP BY 和 AGV/MAX/MIN，搜索工具支持 facet 聚合。Agent 只需要构造出正确的聚合查询，拿到的就是精简的统计结果而不是原始大表。

### 5.2 追问：事后摘要用的 LLM 和主推理用的 LLM 需要是同一个模型吗？有什么考量？

不需要，而且通常不应该是同一个。摘要任务相对简单，用一个便宜快速的小模型就够了，比如主推理用Claude Opus 4.6，摘要压缩用 Claude Haiku 就行.这样既节省成本又降低延迟。但要注意小模型的上下文窗口可能更短，如果摘要的内容本身就很长，可能需要一次机械截断再送去摘要。

### 5.3 追问：分页方案在实际中有没有什么坑？Agent 会不会陷入无限翻页的循环？

会的，这是一个场景的问题。Agent 有时候不知道什么时候该停，会一直翻页直到把所有页都看完。解决办法是在系统 prompt 里明确告诉它翻页预算，比如“最多翻三页，如果三页之内找不到答案就用已有信息回答”。另外工具返回的 total_count 也很关键，Agent 看到总共 50000条记录，自然会意识到不可能全看完，被迫换策略。
